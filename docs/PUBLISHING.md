# Как выложить LivePaint на GitHub

В GitHub отправляются **исходники**, а не вся папка сборки.
`target/` уже исключён через `.gitignore`, поэтому локальные гигабайты кэша
не нужно ни удалять, ни загружать.

Эта инструкция не выполняет публикацию автоматически: команды ниже запускаешь
ты сам, когда будешь готов. Локальный Git-репозиторий и репозиторий на GitHub —
разные вещи: `git init` и `git commit` ещё ничего не отправляют в интернет.

## Что должно попасть в репозиторий

```text
.gitignore
Cargo.toml
Cargo.lock
LICENSE
Makefile
README.md
src/
contrib/
docs/
```

**Не добавляй:** `target/`, архив всей рабочей папки, локальные логи,
личные настройки и скриншоты с приватным содержимым рабочего стола.
`Cargo.lock`, наоборот, оставь: для приложения он фиксирует версии зависимостей.

## 1. Подготовь README

Выбери имя репозитория; ниже используется `livepaint`.
В `README.md` замени `YOUR_USERNAME` на своё имя на GitHub.
Если выбрал другое имя репозитория, поменяй также ссылку и `cd livepaint`.

Локальная папка может по-прежнему называться `paint`: переименовывать её не нужно.

## 2. Создай локальный Git-репозиторий

Открой терминал в папке проекта:

```sh
cd ~/Documents/dev/paint
git init -b main
```

Эта команда нужна только один раз. Если проект уже является Git-репозиторием,
повторять инициализацию не нужно.

Добавь файлы явно — так в первый commit не попадёт случайный мусор:

```sh
git add .gitignore Cargo.toml Cargo.lock LICENSE Makefile README.md src contrib docs
git status --short
git diff --cached --stat
```

Проверь список. В нём должны быть исходники, документация и ресурсы приложения,
**но не `target/`**. Дополнительные проверки:

```sh
git check-ignore target/release/livepaint
git ls-files target
```

- Первая команда должна вывести `target/release/livepaint`: путь игнорируется.
- Вторая не должна вывести ничего: файлы `target/` не отслеживаются Git.

Создай первый commit:

```sh
git commit -m "Initial release of LivePaint"
```

Если Git просит указать автора, можно настроить его **только для этого проекта**:

```sh
git config user.name "Твоё имя или ник"
git config user.email "Твой email для GitHub"
```

После этого повтори `git commit`. Имя и email войдут в историю коммитов.
Если не хочешь публиковать личный email, возьми свой GitHub noreply-адрес
из **Settings → Emails**, а не придумывай его наугад.

## 3. Создай пустой репозиторий на GitHub

1. Открой GitHub → **New repository**.
2. Укажи имя, например `livepaint`.
3. Выбери **Public**, если хочешь поделиться приложением со всеми.
4. **Не добавляй** README, `.gitignore` и лицензию через форму: они уже есть локально.
5. Нажми **Create repository**.

## 4. Отправь исходники

Замени `YOUR_USERNAME` и при необходимости имя репозитория:

```sh
git remote add origin https://github.com/YOUR_USERNAME/livepaint.git
git push -u origin main
```

Если `origin` уже существует, сначала посмотри `git remote -v`, чтобы не отправить
проект в чужой или другой свой репозиторий. Не меняй адрес и не используй force push
вслепую.

Для HTTPS GitHub требует поддерживаемый способ авторизации — например,
GitHub CLI/credential manager или personal access token, **не пароль от аккаунта**.
Не добавляй токен в URL, файлы проекта или README. При настроенном SSH можно
использовать SSH-адрес, который GitHub показывает на странице репозитория.

Готово: GitHub отобразит README на главной странице. Сборочный кэш останется
только на твоём компьютере; Git передаёт отслеживаемые файлы, а не всю папку на диске.

## Как публиковать следующие изменения

Например, после изменения интерфейса:

```sh
git status
git add src/ui.rs README.md
git diff --cached --stat
git commit -m "Update toolbar UI"
git push
```

В `git add` указывай реально изменённые файлы. Не нужно повторно выполнять
`git init` или `git remote add`.

## А если `target/` уже случайно отслеживается?

`.gitignore` не перестаёт отслеживать файлы, которые уже попали в индекс Git.
Для такой ситуации:

```sh
git rm -r --cached -- target
git status
```

`--cached` убирает файлы **из Git**, но оставляет локальную папку сборки на месте.
После проверки создай commit. Это не удаляет большие файлы из предыдущих коммитов:
если они уже попали в историю, перед публикацией нужно отдельно разобраться с ней.
Не делай force push и не переписывай историю, не понимая последствий.

## Нужно ли класть готовую программу в Git?

Нет. В обычном репозитории достаточно исходников и инструкций сборки.
Если позже захочешь раздавать готовый бинарник, приложи **только нужные файлы**
к GitHub Release, а не добавляй `target/` в commit и не архивируй весь проект с кэшем.

У бинарника остаются системные требования: Linux, нужные библиотеки,
Wayland-композитор с layer-shell и рабочий Vulkan-драйвер. Сборка на одной машине
не гарантирует совместимость со всеми Linux-дистрибутивами.
